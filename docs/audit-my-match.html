Synthèse exécutive

Le widget n'est pas seulement « trop lourd » : il est structurellement coûteux (25 ligues interrogées à chaque passage, plusieurs sources qui se chevauchent), fragile (orphelins proot, caches partiels) et vulnérable (valeurs d'équipe concaténées sans échappement shell). Les correctifs P0/P1 conservent toutes les fonctionnalités et réduisent le coût d'environ 92 %.

P0 sécurité. Les valeurs favStr, favTid, favNoTid étaient concaténées brutes entre apostrophes (WANT='…'). Un abbr contenant une apostrophe pouvait exécuter du shell dans le proot. Corrigé par sh() aux quatre endroits + filtrage défensif.
P0 coût. games interrogeait 28 ligues × 4–5 mois = 112–140 requêtes toutes les 15 min. Les ligues sont désormais limitées à celles des équipes suivies (+ CDF/UEFA), avec un cache mensuel immuable : ~5 requêtes par passage.
Validation. Le widget optimisé compile avec le vérificateur OWL du projet (owl check, 184 nœuds, identique à l'original), les 11 scripts passent bash -n, et le lien de partage fait un aller-retour sans perte.

1.2 Détail des comptages (preuves)

Note : l'énoncé « 25 ligues × 5 mois = 125 » sous-estime le code réel. CLUBS compte 25 ligues (L14) plus NATS 3 (L15), soit 28 ; et MONTHS (L56) donne 4 mois distincts la plupart du temps, 5 seulement quand -4 j change de mois. Le vrai coût est 112–140 requêtes/exécution.

  • games : CLUBS = 25 ligues (L14), NATS = 3 (L15) ⇒ 28. MONTHS = -4 0 30 60 90 jours (L56) ⇒ 4 mois distincts en général, 5 quand -4 j change de mois. 28×4 = 112 ; 28×5 = 140.
  • seasonAll : 26 ligues non-calendaires × 13 mois (07→12 puis 01→07, L296-297) + 2 ligues calendaires (nor.1, swe.1, L298-299) × 12 = 338 + 24 = 362 froid. Chaud : une seule requête par ligue (mois courant), car lms saute les autres (L313) ⇒ 28.
  • standings : TABLES compte 26 entrées (L388), dont les 3 coupes UEFA et 2 compétitions nations.
  • teamsDb : LEAGUES compte 27 entrées (L456).
  • extra : LEAGUES = 11 (L535). RR = 6 ligues à 5 mois (L565-566), 5 ligues à 2 mois (L567) ⇒ 6×5 + 5×2 = 40 scoreboard à froid. Chaud : mois courant seulement ⇒ 11. rrun ajoute 6 appels standings à chaque exécution (L614), même avec cache chaud.
  • liveM : LGD (L661-672) construit les couples depuis espn-games.json, espn-season.json, espn-extra-base.json, espn-nextup.json, puis filtre state=="in" ou pre dans [now-5400, now] (L666) et le périmètre myTeams (L667).   • nextup : 11 ligues × 4 mois (0 30 60 90, L826) = 44.

2.4 Défauts qui gonflent le coût

  1. games refetch 4–5 mois à chaque passage (L56-61) : aucun cache mensuel, alors que les mois passés sont immuables. C'est le premier poste de tout le widget.
  2. Filtrage après téléchargement : chaque scoreboard mensuel complet (294 Ko, 30–60 matchs) est téléchargé puis filtré par jq sur 1 à 5 équipes (L48, L279). L'API n'offre pas de filtre équipe : la seule réduction possible est la liste de ligues.
  3. liveM parse 4 caches chaque minute (L661-672) même quand N=0, et sans cache de résultat : 120 jq/h + 60 bash/h inutiles au repos.
  4. extra refetch le mois courant de 11 ligues toutes les 30 min (L573-580) + 6 standings (L614) : chevauchement avec games/seasonAll/nextup/histfull.
  5. n >= 30 (L69-73) : le seuil compte des lignes d'événements, pas des requêtes réussies. Avec une liste de ligues dynamique (moins d'événements), une équipe nationale ou un mois creux peut faire échouer games alors que les réponses sont valides.
  6. Pas de trap : les exit 1 L80, L606, L761, L833, L936 laissent $tmp derrière eux ; les timeouts coupent bash au milieu d'un wait et laissent des curl/fichiers.
  7. Timeouts trop courts dans le pire cas : games 240 s pour 23 vagues × 16 s ≈ 368 s ; standings 90 s pour 96 s ; histfull 150 s pour 176 s.
  8. teamsDb écrase le cache avec un résultat partiel (L500-503) : si une seule ligue répond, les 26 autres disparaissent du catalogue jusqu'au lendemain.
  9. formsData lit /root/.cache/... en dur (L529) alors que tous les autres scripts utilisent ~/.cache : si $HOME != /root, les formes du bandeau sont vides. Utilise aussi /usr/bin/jq en dur.
  10. Caches dupliqués par source : espn-games, espn-season, espn-extra-base, espn-nextup, espn-hist-base, espn-knock contiennent des chevauchements de matchs ; le même mois de la même ligue est retéléchargé par plusieurs sources.

6. Risques de régression et tests

6.1 Risques

  1. t.league absent ou obsolète (état persisté d'une ancienne version) : le fallback liste complète protège, mais il faut le tester.
  2. Équipe nationale : league peut valoir uefa.nations, fifa.worldq.uefa ou fifa.friendly. Le patch ajoute les 3 ; vérifier qu'aucune ne déclenche 3 ligues UEFA de clubs inutiles.
  3. Coupe de France : un club L1/L2 doit voir ses matchs CDF. Le patch ajoute fra.coupe_de_france uniquement pour fra.1/fra.2.
  4. Mois vide : games doit marquer un mois sans match comme récupéré (.ok) pour ne pas le refetcher toutes les 15 min. Tester juin/juillet.
  5. Passage de mois : CUR est local (date +%Y%m), l'API est UTC. Tester le 1er du mois à 00:30 (Europe/Paris) : le mois UTC précédent peut encore contenir des matchs. Le cache mensuel + -4 j couvre le trou, mais vérifier.
  6. Gating liveM : un match qui commence moins de 15 min après le dernier games peut être raté jusqu'au run suivant. Fenêtre 3 h + state=="pre" atténue, mais tester un coup d'envoi imminent et un match qui passe de pre à in sans rafraîchissement de games.
  7. LAST live : si liveM échoue complètement, on ressert l'ancien état ; l'âge liveAt peut vieillir. C'est préférable à un écran vide, mais l'UI doit afficher liveWarn au-delà de 15 min (déjà L1103).
  8. Backfill annuel : dates=YYYY&limit=1000 renvoie 2 saisons dans une année civile. Le filtre keep L329/L921 élimine la saison précédente, mais vérifier les mois de juillet/août. Pic mémoire/transfert : traiter en flux, concurrence ≤3.
  9. curl --parallel : version de curl dans proot inconnue ; --parallel existe depuis 7.66. Tester sur l'appareil avant de généraliser.
  10. teamsDb fusion : si le cache ancien contient des clés obsolètes, elles persistent. Prévoir une purge annuelle ou un champ season.
  11. now 15 s : le spinner (elapsed%10, L1739) et « actualisation Xs » deviennent saccadés. Si c'est inacceptable, garder 1 s ; le gain est uniquement CPU/UI, pas réseau.
  12. Fuseau/strftime dans le backfill : (.at|strftime("%Y%m")) est en UTC, cohérent avec l'API.

1. Coût de rendu

1.1 Modèle de rendu OWL (preuves)

  • Chaque propriété est une expression live ; un let global est un derivedStateOf(structuralEqualityPolicy()) (WidgetInstance.kt:242), et une propriété de nœud est observée via derivedStateOf (Props.kt:58-68). Le runtime documente « a value that comes back unchanged invalidates nothing » (WidgetInstance.kt:170-175) : une valeur identique ne recompose pas.
  • Un for est clé par key(...) (Render.kt:347-357) ; les lignes stables ne sont pas reconstruites quand la liste se réordonne. Mais un for sans key stable, ou une clé dupliquée, perd cet avantage.
  • visible:false sort avant la composition (Render.kt:538) ; if ne compose que la branche active (Render.kt:343). Les deux sont équivalents pour le coût, mais if ne conserve pas l'état de scroll.
  • lazy:true n'agit que sur un for directement enfant du Column/Grid (Render.kt:475-520). Un for dans un if n'est pas lazy.
  • Limites : 500 nœuds pour une tuile, 1000 pour un écran (Compiler.kt:17,20), 2000 ops Canvas/frame (Canvas.kt:74), 32 images bitmap (WidgetImages.kt:241), listes plafonnées à 1000 (Builtins.kt:77). Le compteur de nœuds compile le corps d'un for une fois ; le runtime le multiplie.

1.3 Preuve de l'injection

Le quoting de sh() est correct quand il est utilisé seul : sh("O'Neil") produit 'O'\''Neil' (test amont LangTest.kt:1441-1443). Ici il n'est pas utilisé.

# Valeur favorite : PSG
WANT='PSG'                       # ok

# Valeur favorite : O'Neil
WANT='O'Neil'                    # bash: EOF prématurée -> script mort

# Valeur favorite : '; touch /tmp/PWN; #
WANT=''; touch /tmp/PWN; #'      # exécute touch

# Valeur favorite : x'$(touch /tmp/PWN)'
WANT='x'$(touch /tmp/PWN)''      # exécute la substitution

Précision importante : $(...) ou des backticks seuls, à l'intérieur des apostrophes, restent littéraux. C'est l'apostrophe qui ferme la quote et permet l'exécution. Autrement dit, tout abbr/tid contenant ' est dangereux; $() seul ne l'est pas, mais devient dangereux combiné à '.

1.4 Chaîne d'exploitation

  1. ESPN (ou un cache corrompu) renvoie team.abbreviation = "'; curl … #" ou team.id = "'; … #".
  2. teamsDb écrit ce champ sans validation : ligne 494 (abbr: $t.abbreviation, tid: ($t.id | tostring)).
  3. L'utilisateur sélectionne l'équipe (ligne 1305), myTeams=draft (ligne 1315), l'état est persisté (ligne 1009).
  4. Au prochain games, seasonAll, standings ou liveM, favStr/favTid/favNoTid est concaténé dans WANT et exécuté dans le bash invité.

Impact : exécution de commandes en tant qu'utilisateur Linux invité (pas root Android), lecture/écriture des caches et des répertoires montés, accès réseau. Un widget tiers peut aussi embarquer un state myTeams piégé; il peut déjà lancer des commandes, mais cela montre que la donnée d'état n'est pas une frontière de confiance. L'état myTeams peut également être écrit par owl-send ou par une valeur persistée corrompue : la validation doit donc être faite au moment de construire favStr/favTid/favNoTid, pas seulement dans l'UI de sélection.

2. Données ESPN non fiables

2.1 Parsing

Les filtres supposent des types et des champs parfaits :

  • fromdateiso8601 sur .date[0:16] + ":00Z" (48, 279, 557, 709, 740, 815, 886) : une date absente, courte, avec fuseau ou invalide fait échouer tout le filtre. Comme le flux est redirigé vers un .jsonl, jq peut avoir déjà écrit une partie des événements : fichier partiel conservé.

4.3 Jobs, wait, kill

  • wait sans argument (62, 99, 318, 357, 435, 498, 524, 581, 627, 651, 720, 758, 786, 832, 858, 912, 968, 980) attend tous les jobs du shell. Si un curl/jq se bloque au-delà de son -m, le wait bloque jusqu'au timeout extérieur.
  • Les & (52, 94, 287, 352, 431, 494, 519, 561, 620, 646, 713, 745, 781, 820, 853, 890, 975) laissent des enfants si le shell est tué.
  • Aucun kill dans le widget. C'est bien : un pkill -f espn, kill 0, kill -- -$$ ou killall bash tuerait le GuestShell persistant ou d'autres widgets. Le nettoyage doit rester limité aux jobs du script.
  • Fuite de descripteurs : pas de exec/redirection permanente dans le widget; les FDs des jobs se ferment au wait. Le GuestShell amont garde son fichier $__err par shell persistant (hors périmètre widget), et les fichiers de cache ne sont pas tenus ouverts. Aucun descripteur fuyant identifié dans le widget lui-même.

4.4 trap sûr (ne tue pas le GuestShell)

À insérer au début de chaque script, avant tmp=$(mktemp -d) :

tmp=
cleanup() {
  rc=$1
  trap - EXIT INT TERM HUP
  # Uniquement les jobs de CE bash, jamais le groupe de processus du GuestShell.
  for p in $(jobs -p 2>/dev/null); do kill "$p" 2>/dev/null || true; done
  wait 2>/dev/null || true
  [ -n "${tmp:-}" ] && [ -d "$tmp" ] && rm -rf -- "$tmp"
  exit "$rc"
}
trap 'cleanup $?' EXIT
trap 'cleanup 143' INT TERM HUP

tmp=$(mktemp -d) || exit 1

Pourquoi c'est sûr :

  • jobs -p ne liste que les jobs lancés par ce bash -c; le GuestShell est le parent, pas un job.
  • On ne fait pas kill 0, kill -- -$$, pkill -f, killall, ni kill sur un PID lu dans un fichier.
  • rm -rf -- "$tmp" est protégé par [ -n ] && [ -d ]; jamais de rm -rf "$tmp"/* avec tmp vide.
  • Sur SIGKILL du timeout, le trap ne tourne pas : c'est pourquoi il faut aussi réduire le budget (§4.5) et, côté amont, timeout -k 5 avec GuestShell. Le kill des jobs directs ne tue pas forcément les petits-enfants d'un sous-shell; c'est curl -m 8/--max-time qui borne leur durée. Ne jamais utiliser kill -- -$$ pour compenser : cela peut atteindre le GuestShell.

Ne pas remplacer les rm -rf "$tmp" existants par un trap qui tue tout : les deux peuvent coexister (le rm final est idempotent).

4.5 Réduire le risque sans retirer de fonctionnalité

  • Passer curl -m 15 à --connect-timeout 4 --max-time 8 et augmenter la concurrence de 5 à 8 pour games : 18 lots × 8 s = 144 s < 240 s.
  • seasonAll : 31 lots × 8 s = 248 s < 300 s, ou timeout 360 s. Le cache mensuel fait que seul le premier run est complet.
  • histfull : -m 8 -> 12 lots × 8 s = 96 s < 150 s.
  • standings : -m 8 -> 6 lots × 8 s = 48 s < 90 s.
  • scheds : -m 8 -> 7 lots × 8 s = 56 s < 60 s (ou timeout 90 s).
  • Supprimer la couche bash -c quand c'est possible : cmd(gamesScript) au lieu de cmd("bash -c ${sh(gamesScript)}") (237, 361, 453, 531, 724). cmd prend une expression; à valider avec owl-check. Le timeout vise alors directement le script, au lieu d'un bash qui attend un bash.
  • Côté amont GuestShell : timeout -k 5 N bash -c … pour éviter qu'un enfant refuse de mourir.

5. Réseau

5.1 Constats

  • Toutes les URL sont en HTTPS (site.api.espn.com, a.espncdn.com); aucun http://, aucun -k, pas de vérification TLS désactivée. C'est un point positif.
  • curl n'utilise pas -L : les redirections ne sont pas suivies. Une réponse 3xx n'est pas une erreur -f; le corps peut être du HTML, puis jq échoue.
  • Pas de --proto '=https' : une redirection future ou une URL modifiée pourrait descendre en clair. Les URL sont fixes, mais l'option est peu coûteuse.
  • Pas de --max-redirs 0 explicite.
  • Pas de --max-filesize ni de contrôle de taille après téléchargement. --compressed décompresse avant jq; une réponse énorme ou une bombe gzip peut saturer la mémoire.
  • -m 15/-m 10: pas de --connect-timeout séparé; un DNS lent consomme tout le budget.
  • --retry 0/1/2 --retry-delay 1/2: pas de jitter, pas de --retry-max-time; 429/503 peuvent provoquer des rafales synchronisées entre sources.
  • Concurrence globale : 5 (games), 10 (season), 5 (standings), 6 (teams), 5 (extra), 3 (live), 10 (knock), 5 (nextup), 10 (hist). Un refresh() manuel (1735) peut lancer plusieurs de ces scripts en même temps, en plus des sources périodiques.
  • 404/429 : -f les transforme en échec; certains scripts retombent sur le cache, d'autres non (§3.2).
  • SSRF : pas de host dynamique; $lg vient de listes fixes ou du cache, $d d'une date, $p d'un logo filtré. Risque faible, à condition de valider lg du cache avant de l'utiliser (671, 717-719).

  • Match : {id, league, tag, at, state, detail, squads, tids?, odds?, teams?, home?, away?, stage?, round?, month?, fetchedAt?}. id = league:eventId (L.48). at = epoch UTC calculé par .date[0:16] + ":00Z" | fromdateiso8601 (L.48). state ∈ pre|in|post. home/away peuvent manquer dans liveM/knock/nextup (L.709, 740, 815) : GameRow fait g.home??{} L.1330-1331.

  • liveM ne requête que les ligues/dates avec match in ou pre à ±90 min.
  • Tous les wrappers de sortie sont identiques : tableaux pour matchs/classements/équipes, {rounds,anchors}, {at,items}, {league:[...]}, {cell,cols,w,h,idx}.
  • Les caches sont écrits de façon atomique (mv) et les replis cache fonctionnent.
  • Aucun cache n'est supprimé ou renommé sans migration.
  • Les purges 7 j / 120 j / 1 j / 30 j / saison sont conservées ou justifiées.

5.2 Sélection et identité

  • 1 à 5 équipes, clubs et sélections, avec plafond et messages (L.1268-1321).
  • Recherche par nom, nom court et abréviation (L.1271).
  • tid prioritaire, fallback abréviation, kind c/n (L.6-8, 1071).

  • Équipe sans tid toujours suivie via favNoTid.

  • Équipe active réinitialisée à ALL si elle disparaît (L.1036).
  • Persistance de myTeams, team, draft non persisté comme avant (L.1009-1010).

5.3 Écrans et composants

  • 4 onglets principaux et 3 filtres secondaires opérationnels (L.1120-1140).
  • Hero : prochain match, live, logos, rang, heure, compte à rebours, cotes, formes.
  • Live : score, minute, pastille, âge et warning > 15 min.
  • À venir et résultats : tri, plafond 5, V/N/D, dédoublonnage.
  • Journées : Jn, flèches, bornes, Finales, phases, estimation.
  • Classements : groupes, zones, légende, BP:BC large, équipe suivie en gras.
  • Historique : 9 ligues, rounds, avenir.
  • Rivaux : exclusion des équipes suivies, 4 prochains + 8 récents dans la tuile, Jn par équipe.
  • Top 5 : 5 ligues + ALL, listes et classements.
  • Europe : 3 coupes, phase de ligue, bracket.
  • Arbre : 5 tours dans l'ordre, comptes, message phase de ligue.
  • Rappels 12 h et coup d'envoi : une seule notification, nextDone plafonné.
  • Refresh : spinner, ✓/✗, durée, âge, timeout 245 s.
  • Réglages : langue, taille, équipes.
  • Fermeture.
  • Sections repliables et persistance.
  • Mode large/étroit, S/M/L/XL, FR/EN sans débordement.

5.4 États et résilience

  • Chargement, vide, aucun résultat, saison terminée, aucun classement, bracket vide, échec.
  • Offline avec cache : données affichées + statut d'échec.
  • Offline sans cache : états vides, aucun crash.
  • 429/5xx : retries bornés, pas de boucle, cache conservé.
  • JSON partiel : fusion, pas de perte de mois/ligue.
  • Cache d'une saison précédente : démarrage sans mélange.
  • Changement de mois, de saison, de fuseau, DST.

5.5 Performance et propreté

  • CPU écran allumé < 5 % UID ; my-match < 2 %.
  • CPU écran éteint < 2 % UID ; 0 source active.
  • 0 frame au repos sur 10 s ; ≤ 60 fps ; jank < 1 %.
  • 0 orphelin PPID 1 ; 0 processus > 300 s ; 0 mktemp résiduel.
  • ≤ 10 curl simultanés.
  • Requêtes stables ≤ 150/h (objectif 60), live ≤ 60/h.
  • Coût froid ≤ 2 000 req/24 h et ≤ 100 Mo.
  • Caches ≤ 20 Mo, logos ≤ 1 500/20 Mo, sprite ≤ 2 Mo.
  • Aucun logo > 30 j, aucun fichier partiel.
  • PSS stable (< 50 Mo de delta sur 100 refresh).

5.6 Sécurité et intégrité

  • Aucun secret/token dans le widget ou les caches.
  • sh() conserve l'échappement ; test avec ', ;, $().
  • Les données ESPN ne sont jamais interprétées comme du code.
  • Les URLs et chemins de cache sont inchangés ou migrés.
  • Les erreurs ne loggent pas de données personnelles.
