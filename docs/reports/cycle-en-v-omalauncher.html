Constat central. Le launcher nu n'est pas le problème : 0,03 % d'un cœur écran éteint, aucun WAKE_LOCK, fond statique. La consommation vient de ce qu'il héberge : un script my-match orphelin à 100 % d'un cœur, un widget « now playing » à 111 fps, et Linux/opencode jamais suspendus (≈ 1,2 cœur écran éteint). my-match cumule donc une fuite de processus et un coût de rafraîchissement trop élevé (156 requêtes, logos, jq/curl dans proot).
Portée et limite. L'analyse statique porte sur main (0.12.2) ; l'appareil exécute 0.12.0. Le source de my-match n'est pas encore dans le dépôt : les risques internes non prouvés sont marqués [H] (hypothèse) et seront vérifiés dès récupération du fichier.

Le cycle en V appliqué à Omalauncher

La branche gauche descend de l'utilisateur vers le code ; la branche droite remonte du code vers la recette. Chaque niveau de spécification a un niveau de test correspondant. Les flèches horizontales relient une exigence à sa preuve.

1.3 Contexte d'utilisation

  • Téléphone arm64, portrait, grille d'environ 6 colonnes × 12 lignes, Android 10+ ; Linux est optionnel.
  • Usage principal : écran d'accueil ; ouverture d'apps Android/Linux ; requêtes à un agent ; widgets d'information ; panneau de contrôle ; terminal.
  • Entrées : tactile, clavier physique, manette, micro ; navigation complète sans tactile exigée par la documentation.
  • Réseau intermittent ; Linux et agents peuvent rester actifs écran éteint (problème mesuré par l'audit).
  • Appareil de référence de l'audit : Xiaomi 11T Pro, Snapdragon 888, Android 14 (SDK 34), 8 Go, 1080×2400, 120 Hz.

1.5 Mises à jour et compatibilité

Quatre mécanismes empêchent une mise à jour de casser l'existant (docs/ARCHITECTURE.md:89-140) :

  1. Steps rootfs idempotents (APP/linux/Bootstrap.kt:193-209) avec journal files/rootfs-steps.json; un step modifié reçoit un nouvel id.
  2. Fichiers launcher Owned (mis à jour avec l'APK) ou Seeded (mis à jour seulement si non modifiés, jamais ressuscités) via upgrade/Provisioner (absent de l'instantané; utilisé dans APP/Runtime.kt:102-120).
  3. Formats versionnés {"v": N, "data": …} pour les préférences/JSON, avec migrations; parsing entrée par entrée (docs/ARCHITECTURE.md:113-117).
  4. Niveau OWL Compiler.LEVEL et meta { owl: N }; un widget trop récent est refusé proprement (OWL/Compiler.kt:28, 266-270; docs/ARCHITECTURE.md:117-121).

Les mises à jour système (pacman/mise) sont déclenchées par l'utilisateur et vérifiées au plus toutes les 6 heures (docs/ARCHITECTURE.md:123-129).

  • URL http/https seulement; la requête part d'Android, pas du guest (APP/widgets/WidgetServices.kt:652-704).
  • User-Agent: omalauncher-widgets; redirections suivies manuellement, 5 max.
  • Les en-têtes du widget ne sont envoyés qu'à la même origine que l'URL d'origine; un corps n'est pas renvoyé vers un autre serveur; https→http refusé (APP/widgets/WidgetServices.kt:664-699, 940-966).

  • every par défaut 60 s, minimum 5 s; timeout 1..300 s (OWL/Compiler.kt:768-774).
  • json: true parse la réponse; status: true expose {out,err,code,ok}.
  • Un échec HTTP est retenté au plus tôt après 30 s, ou à l'intervalle s'il est plus court (APP/widgets/runtime/WidgetInstance.kt:752-753, 1115-1116).

  • Une commande longue, un processus partagé entre tous les widgets qui écoutent la même commande (APP/widgets/runtime/Streams.kt:21-47).

Le compteur started évite qu'un onStop retardé de l'ancienne activité n'éteigne les widgets de la nouvelle (APP/widgets/WidgetEngine.kt:193-209).

5. Conception détaillée

DES-01 — Un Runtime unique par processus

Décision. Toutes les ressources longues (proot, serveur Wayland, moteur de widgets, thèmes, marché, services Linux) vivent dans Runtime, créé une fois par processus et exposé aux activités (APP/Runtime.kt:78-100; APP/MainActivity.kt:42).

Invariants.

  • Un seul WaylandServer, un seul WindowManager, un seul WidgetEngine.
  • Les activités ne possèdent pas les ressources; elles les empruntent.
  • Les tâches de fond sont sur un SupervisorJob : l'échec d'une tâche ne tue pas l'écran d'accueil (Runtime.kt:122-124).

Limites. Aucun isolement entre widgets; une fuite mémoire ou un crash natif affecte tout le processus.

DES-02 — « Launcher d'abord, Linux ensuite »

Décision. Le démarrage ne bloque jamais sur Linux; le bootstrap est une tâche séparée, éventuellement précédée du service foreground (Runtime.kt:196-215, 245-259).

Invariants.

  • launcherReady est vrai sans Linux (Runtime.kt:134).
  • Les widgets sans Linux restent utilisables; ceux qui en ont besoin sont des placeholders (WidgetEngine.kt:219-231).
  • Retirer Linux ne supprime que files/arch (Runtime.kt:265-283; Bootstrap.kt:294-311).

Limites. Les fonctions Linux (cmd/stream, terminaux, agents) sont indisponibles tant que le bootstrap n'est pas terminé; une installation peut échouer et être reprise (Bootstrap.kt:232-260). Le service foreground peut être refusé par Android 12+ : le travail continue alors sans lui (Runtime.kt:286-289). Les bridges et le serveur Wayland démarrent une fois et ne sont pas arrêtés à la suppression de Linux (Runtime.kt:296-317).

DES-03 — Données hors rootfs, binds explicites

Décision. Les données partagées launcher/guest sont stockées dans Context.filesDir et bindées par proot vers les chemins Omarchy (APP/LauncherData.kt:16-39; APP/linux/Proot.kt:43-60).

Invariants.

  • Installer/supprimer Linux ne touche pas widgets, style, home, thèmes.
  • hostFile() / guestFile() / guestPath() traduisent les chemins en respectant les binds (Proot.kt:66-95).
  • guestFile() refuse les liens qui sortent du guest (Proot.kt:82-95).

Limites. Un chemin guest absolu n'est pas un chemin Android; toute résolution doit passer par Proot.

DES-04 — Contrat d'exécution proot

Décision. Chaque commande guest est un processus libproot.so --kill-on-exit --link2symlink -0 -r files/arch ... /bin/sh -c. L'environnement est reconstruit (env -i) avec un jeu fixe de variables (APP/linux/Proot.kt:129-180).

Invariants.

  • Pas de root réel (-0 = faux root proot).
  • --kill-on-exit : un proot qui sort proprement tue ses tracees.
  • PATH, HOME, XDG_RUNTIME_DIR, WAYLAND_DISPLAY, backend Wayland, EDITOR, BROWSER, TZ sont déterministes.
  • PROOT_LOADER, PROOT_TMP_DIR, LD_LIBRARY_PATH sont fournis au processus hôte (Proot.kt:201-210).

Limites. Un proot tué par SIGKILL ne tue pas ses tracees; d'où killAll() et killTree() (Proot.kt:182-198; ProcessTree.kt:7-26). --link2symlink change la sémantique des hardlinks; TAR_OPTIONS et MISE_NPM_PACKAGE_MANAGER contournent des incompatibilités connues (Proot.kt:157-166).

DES-05 — Mutualisation des shells guest

Décision. Les sources cmd partagent un ShellPool de 3 GuestShell persistants; les actions run ont leur propre shell (APP/widgets/WidgetServices.kt:152-157; GuestShell.kt:108-130).

Invariants.

  • Un shell exécute une commande à la fois (Mutex).
  • Chaque commande est encadrée par timeout, un marqueur de fin et un fichier d'erreur séparé; la sortie standard ne contient jamais le stderr (GuestShell.kt:53-86).
  • Un shell mort est recréé; retry=false interdit le rejeu d'un effet de bord (GuestShell.kt:38-50).

Limites. Trois commandes lentes peuvent retarder les autres; une commande qui ignore timeout (processus détaché) doit être arrêtée par killTree.

DES-06 — Terminaison déterministe des arbres de processus

Décision. Ne jamais se fier à Process.destroy() seul : parcourir /proc, tuer les descendants puis la racine (ProcessTree.kt:7-26).

Invariants.

  • Les enfants sont tués avant le parent proot.
  • Trois passes couvrent les forks concurrents.
  • destroy() ferme aussi les pipes.

Limites. /proc est filtré par Android; seuls les processus du même UID sont visibles. Un processus qui change d'UID échappe au parcours.

DES-07 — Compilation OWL, version et budget

Décision. Un fichier .owl est compilé en Program (AST + tables de slots) avant toute exécution; les fonctionnalités récentes exigent meta { owl: N } (OWL/Compiler.kt:266-270, 377; OWL/Program.kt:329-400).

Invariants.

  • Compiler.LEVEL = 13 (OWL/Compiler.kt:28).
  • Un widget qui demande un niveau supérieur est refusé avec un message « update the launcher » (Compiler.kt:270).
  • Les erreurs de compilation n'empêchent pas de garder la place du widget (WidgetEngine.kt:885-897).
  • Chaque évaluation est bornée par Budget (200 000 étapes) (OWL/Program.kt:69-101); les erreurs deviennent null + message.

Limites. Le langage est volontairement restreint : pas d'accès Android direct, pas de concurrence déclarative, pas de WebSocket, pas de stockage arbitraire hors state/persist.

DES-08 — Une instance par fichier, réutilisation et adoption

Décision. L'identité d'une instance est le nom de fichier. Un rechargement qui ne change pas le Program garde l'instance; sinon il crée une nouvelle instance et transfère les valeurs compatibles (WidgetEngine.kt:585-630).

Invariants.

  • instances[file.name] est unique.
  • instance(spec) vérifie que le Program est bien le même (WidgetEngine.kt:497).
  • adopt(old) reprend sources/state/sampled par nom et type; un secret ne traverse pas un changement de secretHosts (WidgetInstance.kt:617-635).
  • Les triggers reprennent seen si le type est identique.

Limites. Renommer un state réinitialise sa valeur; un fichier renommé est une nouvelle identité.

DES-09 — Politique de vivacité explicite

Décision. La visibilité n'est pas déduite du rendu Compose mais calculée par isLive(spec), qui combine home, page ±1, app, écran, panneau, keybar et aperçu (WidgetEngine.kt:842-860).

Invariants.

  • Home caché ⇒ sources suspendues, sauf app/écran/panneau/keybar/aperçu.
  • Page voisine préchargée pour un swipe fluide.
  • started est un compteur pour absorber les transitions d'activité.
  • Les dépendances manquantes désactivent l'instance même si la page est visible.

Limites. Aucune exécution en arrière-plan réelle (pas de WorkManager, pas de service dédié aux widgets). Un widget « temps réel » est en retard au retour sur sa page jusqu'à la prochaine échéance ou un refresh().

DES-10 — Ordonnanceur de sources

Décision. Chaque source a sa propre coroutine et sa propre boucle; elle attend la visibilité, exécute, puis attend l'intervalle, un refresh() ou un changement de commande/URL (WidgetInstance.kt:685-768).

Invariants.

  • Plancher d'ordonnancement : 100 ms pour une source (1 s pour un trigger); le compilateur borne déjà cmd/stream à 1 s, http à 5 s et clock à 100 ms. NaN est écarté (WidgetInstance.kt:746-747; Compiler.kt:764-781).
  • Une commande construite à partir d'un state est relancée quand la valeur change, au plus une fois par seconde (WidgetInstance.kt:749-764, 1106-1107).
  • Un refresh() réveille la source sans attendre l'intervalle.
  • Une source dont l'argument est null est en pause et compte comme chargée (WidgetInstance.kt:638-641, 738-745).

Limites. Beaucoup de sources à intervalle court multiplient les réveils; le pool de shells et la déduplication amortissent mais ne suppriment pas le coût.

DES-11 — Frontière HTTP et secrets

Décision. HTTP est exécuté côté Android, avec des règles de sécurité plus strictes que le guest (WidgetServices.kt:652-704).

Invariants.

  • HTTPS obligatoire pour les secrets; http:// interdit pour un state secret (OWL/Compiler.kt:177-181).
  • En-têtes non propagés vers une autre origine; corps non propagé vers un autre serveur; redirection https→http refusée.
  • Réponse 1 MiB max; redirections 5 max.
  • post(...) timeout 30 s, non rejoué (WidgetInstance.kt:1118-1119).
  • Les secrets sont expurgés des rapports (WidgetInstance.kt:592-603).

Limites. usesCleartextTraffic=true autorise http:// pour les données non secrètes (AndroidManifest.xml:47). Pas de certificate pinning ni de proxy configurable.

DES-12 — Streams partagés et linger

Décision. Un seul processus par commande de stream, partagé par tous les widgets abonnés, avec une fenêtre de survie de 5 s (Streams.kt:21-97).

Invariants.

  • Maximum 4 commandes distinctes.
  • Le dernier désabonnement programme la suppression de l'entrée après 5 s.
  • Une fin de commande retire immédiatement l'entrée pour que le prochain auditeur démarre un nouveau processus.
  • Le flux est replay = 1 pour que le nouvel auditeur voie la dernière ligne.

Limites. Un stream qui crache des lignes très vite peut saturer le collecteur; il n'y a pas de backpressure explicite au-delà de SharedFlow.

DES-13 — Triggers et RunLimit

Décision. Les triggers sont des coroutines séparées; RunLimit protège contre les boucles de rétroaction (WidgetInstance.kt:804-882; RunLimit.kt:3-31).

Invariants.

  • every ≥ 1 s et seulement page vivante.
  • at attend par tranches de 30 s pour survivre à la veille.
  • when ne déclenche qu'au front montant.
  • on ignore null (chargement) et peut déclencher au premier valeur avec first.
  • 10 tirs max par seconde et par trigger; au-delà, un seul message « does it change what it watches? ».

Limites. Un trigger qui modifie ce qu'il observe est bridé mais peut encore consommer 10 exécutions/s. Les triggers ne tournent pas hors visibilité.

DES-14 — Persistance atomique et secrets scellés

Décision. Les valeurs persist et secret sont séparées du fichier .owl; les écritures sont atomiques (writeAtomically) et sérialisées.

Invariants.

  • save/seal sont @Synchronized; stop() force le flush.
  • Le fichier secret contient {value, hosts}; il n'est restauré que si les hôtes sont identiques (WidgetInstance.kt:254-295).
  • Un secret ne peut pas être modifié par owl-send (WidgetInstance.kt:915-930).
  • Un fichier supprimé emporte ses valeurs (WidgetEngine.kt:472-481).

Limites. Le secret dépend de la clé locale de l'installation (SecretBox) : une réinstallation ou une sauvegarde restaurée sur un autre appareil ne peut pas le déchiffrer et le redemande (WidgetInstance.kt:254-260). Les valeurs persist ne sont pas chiffrées.

DES-15 — Rendu Compose réactif, frame clock borné

Décision. Les propriétés et let sont des états dérivés; les sources écrivent dans des MutableState. Le rendu ne redessine que ce qui lit la valeur modifiée.

Invariants.

  • FrameClock à 60 fps max, avec décimation à la moitié si le dessin dépasse 4 ms (Render.kt:246-249, 309-318; WidgetInstance.kt:530-558).
  • Si plus rien ne lit time, l'horloge se parque (awaitTimeRead, WidgetInstance.kt:339-373).
  • LocalHomeCovered suspend les animations quand home est couvert (Render.kt:151-152, 292-321).
  • LocalLongPress et LocalRipple distinguent tuile, écran et face (Render.kt:200-210).

Limites. Compose reste sur le thread principal; un Canvas trop lourd est ralenti mais pas exécuté hors thread. MAX_DP=4000 borne les tailles (Render.kt:392-399).

DES-16 — Double stockage du layout

Décision. WidgetLayout garde un cache SharedPreferences pour le démarrage; HomeStore écrit/lit layout.toml, qui devient la source de vérité après le premier chargement (WidgetLayout.kt:58-84, 276-289; HomeStore.kt:55-73).

Invariants.

  • Rien n'est écrit avant engine.loaded (HomeStore.kt:14-15, 55-73).
  • Un layout.toml invalide n'est pas écrasé; les erreurs vont dans home/errors.txt (HomeStore.kt:75-110).
  • Les clés inconnues sont conservées (HomeFile.kt:70-76).
  • Les cellules sont rescalées lors d'un changement de colonnes (WidgetLayout.kt:85-107).

Limites. Deux copies peuvent diverger si le processus meurt entre deux écritures; la réconciliation au démarrage privilégie l'état sauvegardé si le fichier est identique à la dernière écriture connue (HomeStore.kt:60-71).

DES-17 — Marché : revue, SHA-256, approbation

Décision. Le marché lit des catalogues statiques GitHub Pages (index.json, faces.json, apps.json) et n'installe que si le SHA-256 du fichier correspond à celui du catalogue (Market.kt:40-53, 143-171; OWL/market/Catalog.kt:17-18).

Invariants.

  • Un fichier installé est enregistré avec version, commandes, requires et SHA-256 (Market.kt:56-84, 246-279).
  • Un fichier modifié par l'utilisateur/agent est détecté; « update all » l'exclut (Market.kt:122-141, 158-174).
  • Un changement de commandes/requires depuis l'approbation est détecté et l'UI du store demande une nouvelle confirmation (Market.kt:140-141; APP/ui/StoreScreen.kt:595).
  • Les widgets non supportés (owl > Compiler.LEVEL) sont signalés (Catalog.kt:59).

Limites. La confiance repose sur GitHub Pages + le dépôt de revue; pas de signature cryptographique du catalogue au-delà du SHA-256. Un catalogue compromis pourrait publier un SHA-256 malveillant.

DES-18 — Thèmes : palette launcher et configs guest

Décision. ThemeStore est la source unique du thème choisi; StyleStore garde le choix dans style.toml; Palette alimente Compose; GuestThemeConfig rend les templates Omarchy dans le rootfs (ThemeStore.kt:78-84, 402-435; GuestThemeConfig.kt:16-42).

Invariants.

  • La palette est chargée avant le premier frame (Runtime.kt:146; ThemeStore.kt:161-169).
  • OMARCHY_REF épingle la release (ThemeStore.kt:530).
  • Un thème utilisateur écrase fichier par fichier la release (OmarchyTheme.kt:45-48).
  • Les fichiers venant d'un dépôt externe sont filtrés (DENIED_FROM_REPO, OmarchyTheme.kt:11-17, 87-95).

Limites. Un thème peut changer le rendu guest (foot, btop, GTK) mais le compositeur Wayland ne suit pas les couleurs du thème; seuls les clients le font.

DES-19 — Une fenêtre Linux = une tâche Android

Décision. WindowManager crée une activité par fenêtre, avec l'URI omarchy://window/<handle> et les flags NEW_DOCUMENT | MULTIPLE_TASK (Runtime.kt:175-192; AndroidManifest.xml:90-215).

Invariants.

  • LinuxWindowActivity est documentLaunchMode="always", donc une tâche par fenêtre.
  • Les alias donnent un libellé/icône corrects dans Recents (AndroidManifest.xml:101-204).
  • removeStaleWindowTasks() supprime les cartes Recents dont la fenêtre n'existe plus (MainActivity.kt:127-145).
  • Le socket Wayland est dans XDG_RUNTIME_DIR bindé; WAYLAND_DISPLAY=wayland-0 (Proot.kt:17-19, 174, 216).

Limites. Le code du compositeur (wayland/) et wlbridge.c n'est pas dans l'instantané; les invariants de protocole sont ceux de docs/ARCHITECTURE.md:25-52. Les fenêtres cachées ne reçoivent plus de frame callbacks, donc un client peut se figer volontairement.

DES-20 — Diagnostic et mise à jour

Décision. Les erreurs de widget sont écrites en trois endroits : logcat, .errors/<file>.txt pour l'agent guest, et .check/<file>.txt pour owl-check; les aperçus sont rendus dans .preview (WidgetEngine.kt:899-945; Previews.kt:34-72).

Invariants.

  • .errors est écrit par un dispatcher sérialisé (errorWriter) (WidgetEngine.kt:899-927).
  • .check contient sha256, result, preview/screen (WidgetEngine.kt:929-945).
  • .inbox accepte owl-send (set/refresh) et répond ok/error (WidgetEngine.kt:655-679).
  • Les formats sauvegardés sont versionnés (docs/ARCHITECTURE.md:113-121).

Limites. Les erreurs runtime sont dédupliquées; une rafale peut masquer une erreur différente. Les aperçus ne sont pas rendus pour les terminaux (WidgetEngine.kt:706-714).

8. Points d'extension et contraintes pour un widget my-match

8.1 Forme à choisir

  • Tuile (widget "my-match") : scoreboard permanent, size: 3x6 ou 4x5, minSize, page, order. Idéal pour un aperçu du prochain match.
  • Écran (screen { }) : détails, statistiques, rafraîchissement manuel, ouvert par screen(); il reste vivant même home caché.
  • App OWL (app "my-match") : expérience plein écran avec sa propre tâche Android, back, deep links internes; back, onBack, icon.
  • Panneau : seulement si le match est un flux de recherche/commande; sinon un panneau est moins adapté qu'une tuile.

8.2 Sources recommandées

  • API distante : source m = http("https://api.example/match/123") every 60s json (minimum 5 s; 60 s respecte les quotas).
  • Ajouter un timeout explicite (timeout 15) et le mot-clé status si l'UI doit distinguer « pas de réseau » de « 404 ».
  • Ne pas utiliser cmd/stream pour un appel cloud : cela exigerait Linux et ferait passer la requête par le guest.
  • stream uniquement pour un flux local (ex. outil CLI qui pousse des événements); maximum 4 streams globaux.
  • file uniquement pour un cache guest explicitement visible; pas d'accès aux fichiers Android privés.

8.3 Modèle d'état

widget "my-match" {
  meta { owl: 13 }
  size: 3x5
  minSize: 2x3

  state last = null persist
  source m = http("https://api.example/match/123", {Accept: "application/json"}) every 60s json timeout 15 status
  let data = m.ok ? m.out : last
  let stale = m.ok == false
  on m first { if (m.ok) last = m.out }
  onTap: refresh()
}

Invariants à respecter :

  • state initialisé à null puis rempli par on … first; l'UI lit data avec ??.
  • Pour afficher l'âge de la donnée, ajouter source now = clock every 1m et mettre à jour un state updatedAt dans un trigger on m (le trigger ne tire pas si la valeur est structurellement identique).
  • Le mot-clé status donne {out, err, code, ok}; ok est le discriminant fiable.
  • Ne pas mettre de secret dans le fichier : state token = null secret.
  • Un source http sans json renvoie du texte; avec json, la réponse est parsée hors thread principal.

8.4 Visibilité et fraîcheur

  • Le widget ne tourne que si sa page est visible ou voisine, ou si son écran, son app, un panneau qui le montre ou la keybar est ouvert (WidgetEngine.kt:842-860).
  • Au retour sur la page, la source est relancée immédiatement si l'intervalle est dépassé (WidgetInstance.kt:749-761).
  • Aucun réveil en arrière-plan : ne pas concevoir un score « live » qui dépend d'un trigger hors écran.
  • every court (5–15 s) possible mais coûteux; préférer 30–60 s + onTap: refresh().
  • Un trigger every a un intervalle minimum de 1 s (au plus 1 tir/s); les autres triggers restent soumis à RunLimit (10/s). Inutile pour du temps réel.

8.5 Interaction

  • onTap sur la tuile : refresh() ou screen().
  • Dans l'écran : url("https://…") pour ouvrir le site, share(...) pour partager, copy(...), notify(...).
  • open(key) ouvre une app du tiroir; url ouvre un scheme externe.
  • Éviter ask/open dans un trigger : autorisé seulement au premier plan (WidgetInstance.kt:517-525).
  • Les touches (pressKey, typeText, latch) sont réservées aux handlers, jamais aux triggers.

8.6 Sécurité

  • secret uniquement vers https://; le compilateur vérifie l'hôte (OWL/Compiler.kt:177-181).
  • Les en-têtes ne suivent pas une redirection vers une autre origine (WidgetServices.kt:664-699).
  • Ne jamais journaliser un token : report() masque les secrets connus, mais un token concaténé de façon exotique peut échapper; ne pas le mettre dans un message.
  • owl-send ne peut pas écrire un secret (WidgetInstance.kt:915-930).

8.7 Dépendances et distribution

  • Déclarer requires { pacman: [...] } seulement si cmd/stream est utilisé; sinon le widget devient needsLinux (OWL/Compiler.kt:221, 367).
  • Pour un widget sans Linux : http, clock, android.*, images https, state, triggers. C'est le cas recommandé pour my-match.
  • meta { owl: N } avec le niveau réellement utilisé; 0.12.0 peut refuser un widget déclarant un niveau supérieur à son Compiler.LEVEL (§9).
  • Pour le marché : meta { category: "sport" }, nom, auteur, preview; les commandes listées sont revues; le SHA-256 est vérifié à l'installation.
  • Le partage par lien supprime page et order (OWL/market/Share.kt:68-80); la position reste locale.

8.8 Tests et vérification

  • owl-check my-match.owl : compilation, erreurs runtime, aperçu de tuile et d'écran (app/src/main/assets/widgets/README.md:15-27).
  • Vérifier .errors/my-match.owl.txt et .check/my-match.owl.txt.
  • Tester hors ligne : la source doit conserver last et afficher l'ancienne valeur avec un indicateur stale.
  • Tester le retour de page : la valeur doit se rafraîchir sans redémarrer l'application.
  • Vérifier les tailles : 2x3 minimum, texte non tronqué, width/height cohérents avec minSize.
  • Tests unitaires OWL : owl/src/test/kotlin/.../LangTest.kt et MarketTest.kt; ils ne couvrent pas le runtime Android.

8.9 Ce qu'il ne faut pas faire

  • Pas de cmd pour un appel HTTP : dépendance Linux inutile.
  • Pas de stream pour un endpoint qui répond une fois.
  • Pas de polling < 5 s sur http, < 1 s sur cmd/stream.
  • Pas de secret en clair, ni dans un let, ni dans meta.
  • Pas de trigger qui modifie sa propre condition sans garde.
  • Pas de fichier de plus de 500 nœuds (tuile) / 1 000 (écran).
  • Pas de réponse HTTP > 1 MiB; paginer ou réduire côté API.

  7. Les secrets dépendent de la clé locale de l'app (SecretBox); pas de portabilité inter-appareils.
  8. Les state/history non secrets sont en clair sur le stockage privé.
  9. Le compositeur Wayland et le bridge JNI ne sont pas dans l'instantané; leur comportement exact n'a pas été revu ligne à ligne.

3.3 Risques de preuve CI

  • L'instantané ne contient pas scripts/ : l'étape NDK de ci.yml et le fetch-proot de release.yml ne peuvent pas être rejoués tels quels.
  • L'instantané ne contient ni gradlew ni gradle/wrapper ni app/src/main/cpp : le build natif et la CI ne sont pas reproductibles depuis cette copie.
  • Des tests lisent des chemins relatifs inter-modules (owl lit ../app/src/main/assets/widgets) : ils dépendent du répertoire de travail Gradle et sont fragiles hors de cette arborescence.
  • Tests dépendants de l'hôte : /bin/sh, ProcessBuilder, liens symboliques, bit exécutable, locale globale, mesure de temps à 2 s (LangTest.aRunawayRegexGivesUp) — flakiness possible sur runner chargé.
  • Aucun test n'est exécuté sur un APK installé : un succès CI ne prouve pas que l'application démarre.

Marque Signification

0.2 Cotation

  • Probabilité : Certaine (observée ou certaine par le code) > Élevée (> 50 %) > Moyenne (20–50 %) > Faible (< 20 %).
  • Impact : Critique (1 cœur permanent, code arbitraire, données personnelles) > Élevé (batterie, réseau ou fiabilité majeurs) > Moyen > Faible.
  • Sévérité : combinaison probabilité × impact. Critique = action P0 ; Élevée = P1 ; Moyenne = P2 ; Faible = veille.
  • Effort : Faible < 1 h ; Moyen 1–3 jours ; Élevé > 3 jours.

0.3 Limites qui s'appliquent à tout le document

  1. Téléphone en charge pendant l'audit (alimentation « AC ») ; le profil batterie annonce 818 mAh au lieu de 5 000 mAh. Les mAh et les %/h sont des estimations relatives, pas des mesures de décharge ([P] audit §1 et §8).
  2. Échantillons courts (10 s, 30 s, 60 s, 12 s) : adaptés aux charges permanentes, pas aux pics ([P] audit §8).
  3. Pas de root : pas d'historique complet des wakelocks, pas de Perfetto, pas d'accès aux fichiers de widgets ([P] audit §8).
  4. Build installé 0.12.0 (Play du 24/10) vs upstream main au commit 916b318 : l'analyse statique n'est pas exactement le binaire installé ([P] audit §6 et §8).
  5. Source my-match absent : les chiffres 156 requêtes, 13 compétitions, 12 mois, logos et jq viennent de l'audit, pas d'une lecture du .owl. Le cache, l'intervalle, les expressions de date et l'échappement shell sont donc des hypothèses à vérifier dès récupération du source.
  6. Réseau non attribuable : les 63,7 Mo reçus / 114 Mo émis en Wi-Fi sur 2 h sont mesurés pour l'UID dev.omalauncher, qui contient le launcher, le widget et les agents opencode. Ils ne sont pas imputables au seul my-match ([P] audit §2).

0.4 Résumé exécutif

  • Le launcher nu n'est pas le problème : 0,03 % d'un cœur écran éteint, pas de WAKE_LOCK, fond statique ([P] audit §1, §5). L'UID dev.omalauncher concentre pourtant ≈ 68,5 % de la consommation estimée par Android, parce qu'il héberge : un script my-match orphelin à 100,4 % d'un cœur, un widget « now playing » à 111 fps, et Linux/opencode jamais suspendus (≈ 1,2 cœur écran éteint).
  • my-match est un cas de fuite de processus autant qu'un cas de widget trop lourd : 156 requêtes + logos + jq dans proot, puis un bash reparenté à init qui continue après la disparition de son proot ([P] audit §3 P0-1 et P1-6).

  • Priorité : retirer ou réécrire my-match, tuer les orphelins par arbre/UID, figer ou arrêter l'invité écran éteint, puis seulement optimiser les animations et l'écran.

1.3 Coût nominal de my-match vs coût de l'orphelin

Prouvé : le processus orphelin a consommé 100,4 % d'un cœur sur 10 s, 99,6 % sur 60 s écran éteint, et 45 min de CPU pour 46 min de vie ([P] audit §2 et §3 P0-1). 2.2 Fiches détaillées

RISK-01 — Orphelin my-match à ~100 % d'un cœur

Catégorie : performance, batterie, fiabilité. Probabilité : certaine. Impact : 1 cœur permanent, 6–10 %/h, chauffe (39 °C en charge), 2 h 15 de CPU UID. Sévérité : Critique.

Preuve : [P] PID 14568, PPID 1, bash -c … ESPN …, 100,4 % d'un cœur sur 10 s, 99,6 % sur 60 s écran éteint, 45 min de CPU pour 46 min de vie (audit §2, §3 P0-1). [P] Le code documente le phénomène : un proot SIGKILLé laisse ses tracees « spin at full speed » (ProcessTree.kt:7-25). [P] Proot.killAll() ne tue que libproot.so et libproot-loader.so, pas un bash déjà reparenté (Proot.kt:189-198).

Mitigation : retirer/désactiver le widget et tuer l'orphelin immédiatement ; ajouter un watchdog côté app (durée > N s → killTree + rapport) ; ne jamais laisser un source cmd/stream sans plafond ; exécuter my-match au tap, pas en source permanente. Propriétaire : widget (cause), app/upstream (watchdog et kill par UID/arbre).

RISK-02 — 156 requêtes + logos par refresh, sans cache conditionnel prouvé

Catégorie : performance, batterie, réseau. Probabilité : certaine sur le volume, élevée sur la répétition. Impact : radio, temps de réveil, 3–16 Mo+ par refresh ([E]), 624–7 488 requêtes/jour selon l'intervalle ([E]). Sévérité : Critique.

Preuve : [P] 13 ligues × 12 mois = 156 requêtes HTTP, téléchargement de logos, puis jq dans proot (audit §3 P0-1 et P1-6). [P] La documentation upstream recommande http(...) plutôt que cmd("curl ...") et file(...) pour le cache (docs/declarations.md:9-13). [P] http() ne code aucun cache HTTP conditionnel : nouvelle connexion à chaque appel, pas d'en-tête If-Modified-Since/ETag (WidgetServices.kt:652-704). Le cache remoteFile ne concerne que les images/sons, avec 24 h de fraîcheur et 64 Mo (WidgetServices.kt:720-756). [H] Le widget garde peut-être un cache d'historique local (audit dit « met en cache l'historique »), mais cela ne prouve pas la réutilisation des 156 réponses.

Mitigation : une seule compétition et la saison en cours ; http(...) + file("~/.cache/espn.json") ; ETag/If-Modified-Since ; intervalle 30–60 min ; rafraîchissement au tap ; pas de logos ; ne jamais refaire l'historique de 12 mois à chaque run. Propriétaire : widget.

RISK-03 — Reconstruction de 12 mois + jq : CPU, mémoire, stockage

Catégorie : performance, batterie. Probabilité : élevée. Impact : parsing lourd, pression mémoire, écritures, allongement du run. Sévérité : Élevée.

Preuve : [P] 13 × 12 mois et jq/proot (audit §3 P1-6) ; [P] 135 Mo libres, 2,27 Go de zram, 208 Mo PSS launcher (audit §2) ; [P] http() plafonne à 1 Mo (WidgetServices.kt:117, :692-693) ; [H] taille réelle des JSON et mémoire de jq non mesurées.

Mitigation : ne garder que le mois courant ± 1 et la saison en cours ; cache agrégé (matchs à venir, derniers résultats) plutôt que l'historique complet ; parser en flux ; supprimer jq ; plafonner la taille du cache ; libérer les fichiers après usage. Propriétaire : widget.

RISK-04 — http() plafonné à 1 Mo : une saison 13 × 12 peut échouer

Catégorie : compatibilité, fiabilité. Probabilité : moyenne. Impact : source en échec, widget muet ou données partielles. Sévérité : Moyenne.

Preuve : [P] MAX_HTTP_BYTES = 1 shl 20, HTTP_TOO_BIG (WidgetServices.kt:117-120, :692-693). [P] La doc le documente (docs/declarations.md:11). [H] Une réponse « saison » de 12 mois pour 13 ligues peut dépasser 1 Mo ; le script actuel en curl n'a pas cette limite, mais une réécriture naïve en http() la rencontrerait.

Mitigation : une requête par ligue et par mois, réponses petites ; pagination ; cache fichier ; jamais un unique gros JSON ; afficher l'erreur HTTP_TOO_BIG et une valeur en cache. Propriétaire : widget.

RISK-05 — Rate limit ESPN + retry 30 s : tempête et données figées

Catégorie : fiabilité, réseau. Probabilité : élevée. Impact : 429/403, backoff absent, données obsolètes, batterie. Sévérité : Élevée.

Preuve : [P] 156 requêtes en rafale (audit §3 P1-6). [P] Si le widget passe en http(), un échec est retenté après RETRY_MS = 30_000 (WidgetInstance.kt:749-753, :1115-1116), ce qui peut amplifier un rate limit. En cmd, le retry court n'existe pas, mais le script peut boucler ou être relancé. [H] Aucun 429 n'a été relevé pendant l'audit ; l'API ESPN n'est pas contractuelle.

Mitigation : backoff exponentiel + jitter ; respecter Retry-After ; ne pas retenter les 4xx hors 429 ; circuit breaker ; cache ; une requête par ligue ; User-Agent identifiable ; afficher « données du … » plutôt que de marteler. Propriétaire : widget + app.

RISK-06 — Schéma ESPN non contractuel : parser jq cassé

Catégorie : fiabilité, maintenabilité. Probabilité : élevée sur 12 mois. Impact : widget vide, mauvais scores, erreurs silencieuses. Sévérité : Élevée.

Preuve : [P] Les données viennent d'une API ESPN non contractuelle, parsées par jq (audit §3 P1-6). [H] Les champs (events, competitions, competitors, status, date) peuvent être renommés, nuls ou absents ; aucun test de schéma n'est disponible dans le dépôt analysé.

Mitigation : parseur typé et tolérant ; validation de schéma ; fixtures JSON enregistrées ; tests de non-régression ; repli sur le cache ; rapport d'erreur visible dans .errors/. Propriétaire : widget.

RISK-07 — Fuseaux/DST et bornes de mois faux sur 12 mois

Catégorie : fiabilité. Probabilité : élevée. Impact : matchs manquants, dupliqués, dans le mauvais jour/mois ; « aujourd'hui » faux. Sévérité : Élevée.

Preuve : [P] 12 mois et 13 compétitions (audit §3 P1-6). [P] Le guest reçoit le fuseau du téléphone (Proot.kt:153) ; les fonctions de date upstream lisent le fuseau du téléphone par défaut (docs/expressions.md, section Dates). [H] Le widget peut grouper par date locale ou UTC, utiliser des mois de 30 jours, ou calculer « aujourd'hui » une fois pour toutes. L'audit du 25/10/2026 tombe, pour un téléphone en Europe/Paris, le jour du retour à l'heure d'hiver : un bon cas de test.

Mitigation : stocker les dates en UTC ; calculer les bornes de mois avec un vrai calendrier ; passer explicitement le fuseau (fmtTime(..., "Europe/Paris")) ; tester les transitions de mars et octobre ; clé de cache date + zone ; ne pas figer « aujourd'hui » au-delà de minuit. Propriétaire : widget.

RISK-08 — killAll/force-stop ne tuent pas les descendants ; relance

Catégorie : fiabilité, batterie. Probabilité : élevée. Impact : orphelins, 1 cœur, redémarrages en boucle. Sévérité : Critique.

Preuve : [P] Proot.killAll() ne cible que les binaires proot/loader (Proot.kt:189-198). [P] killTree() existe mais n'est appelé que sur stop() d'un shell/stream (GuestShell.kt:102-105, Streams.kt:88), pas sur une mort brutale du processus Android. [P] Après am force-stop, le widget a relancé trois scripts au démarrage (audit §3, mise à jour post-audit).

Mitigation : tuer par UID/cgroup, pas seulement par nom de binaire ; scanner les PPID 1 issus du guest ; watchdog ; désactiver la relance automatique après crash/force-stop ; bouton « arrêter tous les jobs invités ». Propriétaire : app + upstream.

RISK-09 — Streams sans timeout dur ; run 30 s ; cmd jusqu'à 300 s

Catégorie : fiabilité, performance. Probabilité : moyenne. Impact : un stream bloqué monopolise 1 des 4 slots ; un cmd long bloque 1 des 3 shells ; redémarrages toutes les 5 s. Sévérité : Élevée.

Preuve : [P] Streams.open() lance proot.process("exec bash -c …") sans timeout (Streams.kt:75-92) ; MAX = 4 (:95) ; un stream qui sort est relancé après 5 s (WidgetInstance.kt:724-725). [P] GuestShell applique timeout (défaut 10 s) mais pas de SIGKILL de l'arbre (GuestShell.kt:38-50, :64). [P] run(...) dure 30 s (WidgetServices.kt:644-650). [P] Le timeout d'un source est borné à 1–300 s (Compiler.kt:766-781). [P] RunLimit ne limite que les triggers, pas les sources (RunLimit.kt:1-30).

Mitigation : timeout dur sur tout processus invité, y compris stream/run ; timeout -k + killTree ; pas de stream pour des scores ; un seul stream ; watchdog ; rapport d'erreur. Propriétaire : app + upstream + widget.

RISK-10 — Injection shell via données ESPN non échappées

Catégorie : sécurité. Probabilité : faible-moyenne (source absent). Impact : exécution de commandes arbitraires dans le proot, exfiltration, destruction. Sévérité : Critique.

Preuve : [P] Un widget cmd exécute du shell par conception ; les valeurs doivent passer par sh() (commande) ou enc() (URL) (docs/declarations.md:57-81). [P] Le compilateur signale les commandes construites avec des valeurs non échappées et les classe comme risquées (Review.kt:209-234). [P] shellQuote() protège la commande entière pour le bash externe, pas les interpolations internes. [H] Si my-match écrit curl "...team=${team}" ou jq "...${name}..." avec des valeurs ESPN, une apostrophe, un $() ou un backtick peut casser le quoting.

Mitigation : ne jamais interpoler de données distantes dans une commande ; identifiants numériques validés ; jq --arg ; sh()/enc() ; tests avec noms d'équipes piégés ; préférer http() + json à curl/jq. Propriétaire : widget.

RISK-11 — Widget partagé/store non fiable = code arbitraire dans proot

Catégorie : sécurité. Probabilité : moyenne. Impact : lecture de fichiers invités, exfiltration réseau, modification des widgets/thèmes, déni de service. Sévérité : Critique.

Preuve : [P] Un widget est du code : cmd, stream, run, Terminal, ask exécutent des commandes ([P] docs/declarations.md:9-13, docs/handlers.md:38-50). [P] Le partage par lien/QR contient le fichier entier ; l'import liste les commandes et signale les risques, mais n'exécute pas dans une sandbox (docs/sharing.md). [P] Le proot lie ~/.config/omalauncher/widgets, ~/.local/share/omarchy, ~/.config/omalauncher/style, ~/.config/omalauncher/home, les thèmes et les fonds, et monte /dev, /proc, /sys (Proot.kt:43-60, :129-180). [P] L'utilisateur est root factice dans l'invité. [P] La revue du store est une barrière de publication, pas une sandbox d'exécution ; un .owl modifié après review peut changer.

Mitigation : n'installer que des widgets relus ; diff avant import ; désactiver cmd/run pour les widgets partagés jusqu'à opt-in ; allowlist réseau ; isolation par UID/sandbox ; ne pas lier les secrets ; CI de review. Propriétaire : upstream + app.

RISK-12 — usesCleartextTraffic=true et http() accepte http://

Catégorie : sécurité, vie privée. Probabilité : moyenne. Impact : interception/modification des scores et logos, fingerprinting. Sévérité : Élevée.

Preuve : [P] android:usesCleartextTraffic="true" (AndroidManifest.xml:47). [P] http() accepte explicitement http:// (WidgetServices.kt:660). [P] Les secrets sont limités à HTTPS (Compiler.kt, règle des secrets), mais les scores et images ne le sont pas. [P] Les images web exigent HTTPS (docs/declarations.md), mais curl dans le proot n'est pas couvert par cette règle ni par la NetworkSecurityPolicy d'Android.

Mitigation : usesCleartextTraffic="false" + networkSecurityConfig ; HTTPS obligatoire pour ESPN et les logos ; allowlist de domaines ; pas de curl pour les données ; vérifier les redirections. Propriétaire : upstream + app.

RISK-13 — ACCESS_LOCAL_NETWORK + URLs arbitraires : SSRF/LAN

Catégorie : sécurité. Probabilité : faible-moyenne. Impact : scan du réseau local, accès à des services domestiques, exfiltration. Sévérité : Élevée.

Preuve : [P] Permission ACCESS_LOCAL_NETWORK déclarée, demandée depuis les réglages, commentée « Android 17+ » (AndroidManifest.xml:5-7). [P] http() accepte n'importe quelle URL http(s), sans allowlist d'hôte (WidgetServices.kt:652-704). [P] Un widget partagé peut donc viser 192.168.x.x, localhost ou un DNS interne. [H] L'application effective de la permission au trafic natif du proot reste à vérifier.

Mitigation : ne pas demander la permission si elle n'est pas nécessaire ; politique réseau par widget ; bloquer les IP privées/link-local pour les widgets ; pas de requêtes arbitraires depuis un widget non relu ; audit des URLs. Propriétaire : upstream + app.

RISK-14 — Logos : téléchargements, décodage, mémoire, vie privée

Catégorie : performance, batterie, vie privée. Probabilité : élevée. Impact : 2,6–13 Mo+ par run ([E]), décodage, cache, requêtes tierces. Sévérité : Moyenne.

Preuve : [P] Téléchargement de logos (audit §3 P0-1). [P] WidgetImages garde au plus 32 images, les décode à 1080 px max, avec un plafond de 32 Mo par bitmap (WidgetImages.kt:241-259) ; le cache disque des fichiers web est de 64 Mo (WidgetServices.kt:136, :757). [H] my-match télécharge peut-être les logos à chaque run dans le guest, sans cache conditionnel.

Mitigation : initiales/abbréviations au lieu des logos ; aucun logo sur l'accueil ; cache local et conditional GET ; charger seulement les logos visibles ; plafonner le nombre et la taille. Propriétaire : widget.

RISK-15 — Now-playing à 111 fps redessine tout l'accueil

Catégorie : performance, batterie. Probabilité : certaine. Impact : 37 % d'un cœur + GPU, 0,5–1 W, 3–5 %/h pendant l'audio. Sévérité : Élevée.

Preuve : [P] 2 833 frames en 30 s, 111 fps audio en lecture, 0 frame en 12 s audio en pause ; RenderThread 34,4 %, main 15,7 % ; diff limité à la barre de progression (audit §2, §3 P0-2).

Mitigation : widget statique (titre + bouton) ; progression par pas de 1 s ; égaliseur supprimé ou ≤ 30 fps ; aucune animation quand la tuile n'est pas visible ; pause = aucune frame. Propriétaire : widget now-playing + upstream.

RISK-16 — Linux/proot jamais suspendu + exemption Doze

Catégorie : batterie, fiabilité. Probabilité : élevée. Impact : ≈ 1,2 cœur en veille, 8–10 %/h, téléphone jamais au repos. Sévérité : Élevée.

Preuve : [P] Écran éteint 60 s : football 99,6 %, opencode serve 13,3 %, TUI 7,2 %, launcher 0,03 % ; UID exempté de Doze ; LinuxService FGS specialUse (audit §2, §3 P0-3 et P1-4). [P] MainActivity.onStop() → Runtime.screenStopped() ne désactive que les substituts /proc ; il ne gèle ni ne tue le proot (MainActivity.kt:201-208, Runtime.kt:410-413). [P] --kill-on-exit ne s'applique qu'à une sortie propre (Proot.kt:132, :182-198).

Mitigation : arrêter Linux après N minutes écran éteint, ou freezer le cgroup invité ; retirer l'exemption Doze ; ne garder LinuxService que si l'utilisateur choisit « agents en veille » ; arrêter opencode serve/TUI quand inutilisés. Propriétaire : app + upstream + utilisateur.

RISK-17 — Redémarrage/force-stop relance les jobs sans backoff

Catégorie : fiabilité, batterie. Probabilité : élevée. Impact : rafale possible de 156 requêtes à chaque démarrage, reprise des scripts, orphelins. Sévérité : Élevée.

Preuve : [P] Après force-stop, le widget a relancé trois scripts ESPN au redémarrage, terminés en ~1 min (audit §3 post-force-stop). [P] Les sources démarrent dès que la page est live (WidgetInstance.kt:694-695, WidgetEngine.kt:629). [P] Aucun backoff persistant ni compteur d'échecs n'est visible dans le moteur ; RETRY_MS ne s'applique qu'aux échecs http en mémoire (WidgetInstance.kt:749-753).

Mitigation : persister dernier run/dernier échec ; backoff exponentiel ; pas de run automatique après force-stop/crash ; démarrage au tap ; limite de runs par heure ; bannière « dernier essai ». Propriétaire : widget + app.

RISK-18 — Pression mémoire : 135 Mo libres, zram, jq/JSON

Catégorie : performance, fiabilité. Probabilité : moyenne. Impact : swap/zram, OOM, lenteur, tués de processus. Sévérité : Élevée.

Preuve : [P] 135 Mo libres, 2,27 Go de zram utilisés, launcher 208 Mo, opencode 428 Mo, TUI 210 Mo (audit §2). RISK-19 — 120 Hz + luminosité + timeout 600 s

3.2 Secrets

  • Le moteur prévoit des états secret chiffrés (SecretBox) et le compilateur limite leur usage aux en-têtes/URL de http()/post() ([P] docs/handlers.md:121-158 ; WidgetInstance.kt:668-672, :986-995). Non audité ici : la solidité de SecretBox, la sauvegarde Android et la protection contre une extraction par root.
  • my-match n'a vraisemblablement aucun secret : ESPN est public. Le risque de secret vient des widgets partagés qui demandent un token et l'envoient à leur propre serveur, ou d'un .owl qui contient un token en clair.
  • Un widget malveillant n'a pas besoin de lire le fichier de secrets : il peut demander le token à l'utilisateur via Input { password: true } et l'envoyer à son serveur, écrit en clair dans l'URL ou les en-têtes. La revue liste le serveur, mais l'utilisateur peut accepter.

3.3 Injection shell et données non fiables

  • cmd/stream/run sont du shell arbitraire par conception. Ce n'est pas une faille du moteur, mais une surface d'attaque pour tout widget non relu.
  • Les valeurs doivent passer par sh() (commande) ou enc() (URL). shellQuote() protège la commande entière, pas les valeurs interpolées à l'intérieur ([P] GuestShell.kt:59-65).
  • Review.kt signale les motifs dangereux (téléchargement envoyé directement à un shell, eval, sudo, lecture de .ssh, URL construite avec des valeurs, etc.) mais ce sont des avertissements, pas des blocages ([P] Review.kt:209-234).
  • Les données ESPN (noms d'équipes, IDs, URLs de logos) sont non fiables. Si elles entrent dans une commande sans échappement, une injection est possible. Hypothèse tant que le source n'est pas lu.

3.4 Réseau clair et SSRF

  • usesCleartextTraffic="true" autorise HTTP pour toute l'app (AndroidManifest.xml:47) ; http() accepte http:// (WidgetServices.kt:660).
  • Les secrets sont limités à HTTPS par le compilateur ; les scores, logos et curl ne le sont pas. curl dans le proot n'est pas couvert par la NetworkSecurityPolicy d'Android.
  • http() n'a pas d'allowlist d'hôte : un widget peut viser localhost, 192.168.x.x ou un DNS interne. C'est un risque SSRF/scan LAN, aggravé par ACCESS_LOCAL_NETWORK.
  • Ce qui est déjà bien : redirections plafonnées à 5, en-têtes non transmis à un autre origin, pas de downgrade HTTPS→HTTP, images web HTTPS seulement, réponse plafonnée à 1 Mo (WidgetServices.kt:117-122, :665-693). Mais cmd("curl ...") contourne toutes ces protections.

3.5 Partage public

  • Un widget partagé par lien/QR contient le fichier entier ; le lien ne passe pas par un serveur (fragment #), mais le widget peut contacter son propre serveur à l'exécution (docs/sharing.md).
  • L'import liste les commandes et signale les risques ; l'utilisateur doit pouvoir refuser. Il n'y a ni signature, ni sandbox, ni limite de permissions au niveau du widget.
  • my-match ne semble pas contenir de donnée personnelle, mais un .owl peut embarquer des favoris, des chemins, des URLs ou des tokens. Le partage doit être relu.
  • Les rapports d'audit et les mesures brutes peuvent aussi fuiter (PIDs, réseau, logs). Voir RISK-23.

4. Fiabilité

4.1 Chaîne de l'orphelin

  1. Un source cmd exécute bash -c … dans un proot, via un shell partagé ([P] GuestShell.kt:38-68).
  2. Le script interroge l'API pour 13 × 12 ([P] audit §3 P1-6) et lance curl/jq ([P] audit §2).
  3. Si le proot est tué brutalement (force-stop, OOM, crash), ses tracees sont reparentées à init et continuent ; --kill-on-exit ne s'applique qu'à une sortie propre ([P] Proot.kt:132, :182-198).
  4. Proot.killAll() ne tue que les binaires proot/loader, pas le bash reparenté ([P] Proot.kt:189-198).
  5. Le widget n'a plus de handle sur ce processus ; il tourne à 100 % d'un cœur, écran éteint, jusqu'à un kill manuel ou un reboot ([P] audit §2).

4.3 Doze, force-stop, redémarrage

  • Doze : l'UID dev.omalauncher est dans la liste blanche ; LinuxService est FGS. screenStopped() ne coupe que les substituts /proc. L'invité n'est ni gelé ni tué ([P] audit §3 P0-3/P1-4 ; MainActivity.kt:201-208 ; Runtime.kt:410-413).
  • Force-stop : tue l'UID (audit : l'orphelin est mort), mais le widget relance ses scripts au démarrage suivant ([P] audit §3 post-force-stop). Linux/opencode sont aussi arrêtés, puis relancés par le terminal.
  • Redémarrage : le launcher est HOME ; il démarre, recharge les widgets, et les sources redeviennent actives dès que la page est visible ([P] WidgetEngine.kt:601-629, WidgetInstance.kt:694-695). Aucun backoff persistant, aucun « ne pas relancer après crash ».
  • Crash/OOM : killTree() n'est appelé que sur stop() ; une mort du processus Android laisse les enfants. C'est le scénario exact de l'audit.

4.4 Observabilité manquante

  • Les erreurs de widget vont dans .errors/ (WidgetEngine.kt:84-100), mais il n'y a pas de CPU/réseau par widget, ni de liste des orphelins, ni de dernière durée d'exécution ([P] audit §6, recommandation « Diagnostic »).
  • Sans cela, un widget peut tourner à 100 % sans que l'utilisateur le sache, et une régression après réécriture est invisible.

5.1 Ce que l'audit prouve

5.3 Arithmétique et scénarios

  • 156 = 13 × 12 : si le widget parcourt 13 compétitions sur 12 mois, chaque refresh complet fait au moins 156 requêtes, plus les logos et les classements.
  • Par jour : 4 h de visibilité et un refresh horaire = 624 requêtes/jour ; toutes les 30 min = 1 248 ; toutes les 5 min = 7 488. Si les trois scripts sont concernés, multiplier.
  • Données : à 50 Ko/requête, 7,8 Mo par refresh ; à 100 Ko, 15,6 Mo. Les logos ajoutent 2,6–13 Mo par run. Sur mobile, cela peut représenter des centaines de Mo par mois.
  • CPU : un refresh nominal d'une minute n'est pas 1 cœur permanent ; l'orphelin, lui, a tourné 45 min. C'est le cycle de vie qui transforme une rafale en charge permanente.
  • Pic de 156 requêtes : sur une connexion mobile, le débit et la radio restent actifs plusieurs dizaines de secondes ; le téléphone peut chauffer et le run dépasser le timeout de 10 s ([E]). Si le widget a mis timeout 300, il bloque un shell partagé jusqu'à 5 min.
  • Fuseau/DST : un match à 00:30 local peut basculer de jour ; un mois de 31 jours peut être tronqué par un calcul fixe ; le 25/10/2026 est un dimanche de changement d'heure en Europe. Un test DST est indispensable.
  • Schéma : une réponse vide, un null ou un champ renommé peut faire échouer tout le jq et laisser le widget vide ; sans validation, l'utilisateur ne voit qu'un écran figé.
  • Rate limit : une rafale de 156 requêtes peut déclencher 429/403 ; si le widget passe en http() et réessaie toutes les 30 s, il amplifie la limite. Un cache et un backoff sont plus efficaces qu'un retry agressif.
